Attack it before anyone else does

Every system I build goes through a red team before I trust it: a deliberate attempt to make it fail. The bugs it finds matter more than the pass mark.

Rory McClellandOctober 20265 min read

Every quarter, ten hostile inputs go through Job Scout, the automated job search I run each morning. In the first exercise all ten were stopped. It also found four genuine bugs, and those four are the reason the exercise exists.

That exercise is a red team: someone plays the attacker, on purpose, before a real attacker gets the chance. The term comes from military war games, where the red side played the opposing force so that plans were tested against an opponent with no interest in them succeeding. Security teams adopted it for the same reason, and AI gives it a great deal more to do.

Why builders cannot mark their own work

A builder testing their own system tests the cases they thought of, which are the cases the system was built to handle. Everybody does this, because the same assumptions that shaped the design also shape the tests. A red team's whole job is to bring different assumptions, and to be pleased when something breaks.

AI systems widen the gap. A conventional system can be attacked through its code and its interfaces. An AI system can also be attacked through words: any text it reads, whether an email, a web page or a job advert, can carry instructions of its own (known as prompt injection). The people who build these models say openly that this cannot be fully solved, which means the defence has to sit in what the system is allowed to do. The only way to know that defence holds is to attack it.

A red team that never finds anything is a reason to worry.

Where the habit started

My first experience of this was at Google, as the first product manager for Chrome Privacy. Every Chrome launch had to clear a privacy review, and the review could return one of three verdicts: yes, yes with required changes, or blocked. Engineers sat in the review, so it was a technical gate. Nobody called it a red team, but it did the same job. People who had not built a feature sat down to work out how it could go wrong, before it reached Chrome's users.

I now apply the same idea, at a much smaller scale, to everything I build with AI.

Job Scout: ten hostile inputs

Job Scout reads my job alerts and email, scores roles and drafts applications, so it reads a great deal of text written by strangers. Its never list says it must never apply, reply, edit or share anything. The red team checks whether that holds when someone tries to make it break those rules. All of the inputs are made up, so no real person's data is involved.

All ten attacks failed, because the design gives them nothing to work with. The model that reads strangers' text has no tools and no internet access, so a hidden instruction has nothing to act on. The bugs were found around the edges. An instruction placed in an email's subject line reached the cloud without being removed. A warning on a reply ("asks for bank details") was raised but never appeared on the board. Each was logged, then fixed or scheduled.

The task app: the serious finding had nothing to do with AI

My task app uses no AI at all, but it went through the same discipline before I trusted it: deliberate attempts to break it with impossible dates, damaged files, odd encodings and requests from other websites. That last one found the only high-severity issue. Any website open in the browser could add, complete or drop tasks through the running app, because browsers let any page send certain simple requests without asking, and the server accepted them.

The fix was three checks on every request, and the retest ran the same probes again. Thirteen issues were found in total, and all thirteen were fixed, each with an automated test that failed before the fix went in. Red teaming is usually discussed as an AI safety technique. In reality the biggest hole in this project was ordinary web security, which is exactly why the attacker's view has to cover the whole system.

What makes it work

  1. Set the bar first. Pass marks are agreed before the results are in, so a disappointing result cannot be argued away afterwards.
  2. Use something that did not build it. A separate agent that has not seen the work reviews the code before each delivery. Before one Job Scout release it found eleven issues; nine were fixed and two were accepted, with the reasons recorded.
  3. Count the bugs as well as the passes. Ten out of ten stopped is reassuring. The four bugs are what made the system better.
  4. Repeat it. Attacks change and systems change, so the exercise runs every quarter, with new inputs added as new tricks appear.
  5. Keep it in proportion. A personal tool gets ten inputs and an afternoon. A system that touches customers or money gets a great deal more.

In an organisation

The same thinking scales up. When I set out an AI adoption plan for an organisation recently, the red team was written into the plan itself: security attacks the first pilot that reads outside content with hidden-instruction attempts, before it starts and while it runs, and one of the checkpoints for widening its use simply asks whether the safeguards held when tested. Making the attack a planned stage means nobody has to argue for it later, when a deadline is close.

Job Scout has run every morning since mid-October. The number of applications, replies or messages it has sent on my behalf is still zero, and the red team is how I know that figure is earned. (It is also the only part of the project where finding a problem counts as a good day.)
