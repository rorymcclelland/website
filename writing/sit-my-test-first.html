Sit my test first

A new open coding model posts 89.7% on a leading benchmark. Before any model goes near one of my builds, it sits my own evaluation, on my own data, against my never list.

Rory McClellandOctober 20265 min read

This week a company called Recursive released Flint, an open-weight coding model under the Apache 2.0 licence. The headline figure is 89.7% on SWE-bench Pro v2, a benchmark built from real software engineering tasks. Flint has about 40 billion parameters but uses only around 2.5 billion for each token it produces, so the coverage quickly turned to running it on your own machine.

I build agents that do part of their work on a local model, so I read the announcement with interest. Then I read the model card, which is a more careful document.

What the card says

The card calls the scores ‘release evaluations’. It says some comparison figures were measured by Recursive and others were reported by their developers, but it is not clear which applies to the headline numbers. Its hardware guidance is one data-centre GPU per copy of the model, and the full-precision download is about 80 GB. Laptop figures are circulating for community-made compressed versions, which are someone else’s test of someone else’s build.

The card also says something I agree with completely: a model that calls tools can still make unsafe choices, so the application has to enforce its own permissions and boundaries.

None of this makes Flint a bad model. It may be excellent. The headline number just answers a different question from the one I need answered, which is whether it can do my job, on my data, without breaking the rules I have set for it.

My test, on my data

Job Scout, my private job search agent, reads job adverts on the local PC with a local model. The model has no tools and must return a fixed shape. Every requirement or pay figure it extracts is kept only if those words appear in the advert, and only the checked job spec leaves the machine.

Choosing that model was a measurement exercise. In the first spike I ran two small models over real adverts:

Both invented requirements for a page that had no text on it at all, which takes some imagination. No leaderboard would have shown me that.

I added checks, then retested on about 20 adverts plus one hostile advert written to trick the reader. The bar, set before the run, was 9 out of 10 right on must-haves and pay. The 14 billion model passed 21 of 22, and the three failures became three fixes before its output was allowed anywhere near the scores.

The RFI tool I am building now follows the same rule, written into its decision record: pick the model by measurement. Three embedding models will answer the same English and Japanese questions before one is chosen, and the hosted and local defaults are chosen separately.

A leaderboard tells you a model can pass an exam. Only your own test tells you whether it can do the job.

Why the leaderboard drifts from your work

There are three reasons, and I have run into all of them.

  1. Your data is messier. Benchmarks are curated. Job adverts, RFIs and internal documents arrive half-formatted, duplicated, in two languages or, as above, empty.
  2. Your failures are different. A benchmark marks a task as passed or failed. I care most about what happens on the hostile input, the empty page and anything on the never list, and those cases are rarely in anyone else’s test set.
  3. Benchmarks become targets. In July, OpenAI disclosed that two of its own models, under test on an internal security benchmark, escaped their test environment and broke into Hugging Face’s production systems to fetch the benchmark’s solutions. Any score that is published and celebrated will be optimised for, by people and increasingly by models.

Anyone who has run a product will recognise this. A metric someone else chose tells you about their goals. It is fair to say that your own evaluation set is the only score that measures yours.

What Flint would have to pass

I may well try Flint. A small active size and an open licence are exactly what a local-first build wants. If I do, it gets the same treatment as every other model:

  1. Write the bar down first, so the result cannot move the goalposts.
  2. Run it on my own evaluation set, including the hostile inputs, side by side with the model it would replace.
  3. Measure speed and memory on the local PC, the machine it would actually run on, using the compressed version I would actually use.
  4. Keep it tool-less. Permissions live in the application, as the card itself advises.
  5. Re-run the test when anything changes. The card notes that results vary with precision and runtime, so a new version is a new model as far as I am concerned.

For product leaders the lesson is simpler still. When a team proposes a new model, ask one question first: what did it score on our test? If there is no test, building one is the first piece of work, and it will outlast every model you put through it.
