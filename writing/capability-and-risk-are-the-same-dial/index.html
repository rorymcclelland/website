Capability and risk are the same dial.

Each step an AI system takes towards working on its own makes it more useful, and makes a mistake more costly. The two move together, so they have to be managed together.

Rory McClelland · October 2026

When a team first sees an AI agent do something useful on its own, the next question is almost always the same: how quickly can we let it do more? It is a fair question. It is also the point at which most rollouts take on risk that nobody has priced.

One dial, two readings

Every increase in what a system is allowed to do is also an increase in what it can get wrong. A system that drafts a reply can produce a bad draft. A system that sends the reply can send a bad one to a customer. The capability gained and the risk taken on are the same change, read from opposite ends.

That sounds obvious written down, but it is rarely how the decision gets made. Capability tends to be argued for by the people who want the benefit, and risk is assessed later by different people, often once the system is already live. (By then, the review tends to read like an apology.)

Four stages, each one earned

The same four stages run through the method, where each one has its own worked examples.

The way I approach it is to treat autonomy as something a workflow earns in stages, each with its own test for moving on.

  1. Shadow. The system runs on live data, but nobody acts on what it produces. It moves on once its agreement with human judgement has settled, and the disagreements are understood.
  2. Assisted. It recommends, with the evidence behind it, and a person decides. It moves on once corrections are rare and still falling, and the people using it every day trust it.
  3. Delegated, within bounds. It acts on its own inside set limits: value limits, particular case types and confidence thresholds. Anything outside them goes to a person.
  4. Extended authority. The limits are widened as evidence builds, and reviewed against measured performance, never simply because time has passed.

Each step forward is paid for with evidence from the step before, so capability is only added once the risk that comes with it has been measured.

What it looks like in practice

A never list: what a system must never do, agreed before anything is built and enforced by design.

I applied the same thinking to my own job search tool. It reads job adverts and emails every morning, scores the roles and drafts applications for the best few. It never applies, replies or contacts anyone. Those actions sit on a never list agreed before any code was written, so the worst it can do is produce a draft that I then decide not to send.

If I ever wanted it to send applications on its own, that would be a new stage, with its own evidence to gather first.

A better question

So the question worth asking is: what would we need to see before we let it do more? That question has an answer that can be measured, which makes it a great deal easier to say yes to.
