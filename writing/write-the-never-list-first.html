Write the never list first

Before deciding what an AI system should do, I write down what it must never do. Then each line is made true in code.

Rory McClellandOctober 20263 min read

Most AI projects start with the exciting list: everything the system will be able to do. I start with a shorter one. Before a single story is written, I agree what the system must never do, and that list becomes the most important requirement in the backlog.

For Job Scout, the automated job search I run every morning, the list has four lines:

  • Never apply for a role.
  • Never reply to or follow up any message.
  • Never edit my LinkedIn profile or a sent document.
  • Never share the board or change the rules.

Each line protects something that cannot be taken back. An application sent with an overstated claim cannot be withdrawn, and one message sent without my knowledge could damage a relationship with an employer. A job search is ideal work for automation. The data it runs on, a private mailbox and a career record, is exactly the kind that should not be handed to automation casually.

Making each line true in code

Writing "never send email" into an AI agent's instructions is a start. Instructions can be misread, ignored or overridden, and text written by strangers (a job advert, a recruiter's email) can carry hidden instructions of its own. So each line of the never list is also made true by design:

The question I ask of every line is simple: if the AI decided to do this anyway, what would stop it? If the only answer is "it was asked not to", the line is not finished yet.

The list shapes the rest of the design

Once the never list exists, a lot of later decisions become easier.

Which steps become AI agents. A step becomes an agent only when it needs isolation, independence or on-demand use, and everything else is ordinary code that can be tested exhaustively. The model that reads adverts written by strangers holds nothing valuable and has no tools, so a hidden instruction in an advert has nothing to act on.

Read-only first. Write access is earned with evidence.

How authority grows. Job Scout can suggest moving a card on my board, for example to Rejected after a rejection email arrives. It cannot move the card by itself until I have graded its reply reader against my own judgement, so until then every move is a suggestion with Confirm and Dismiss, logged and reversible.

How it is tested. Every quarter, ten hostile, made-up inputs go through the real system: hidden instructions in adverts and subject lines, a request to send data elsewhere, a fake recruiter, and a fake job offer asking for bank details. In the first exercise all ten were stopped, and it still found four genuine bugs (which is rather the point of doing it).

Writing one for your own system

A never list suits any AI system that touches something people rely on, and the first draft takes about an hour.

  1. List what cannot be undone: sending, paying, deleting, publishing, signing, contacting a customer.
  2. List what must not leave: which data must never reach which part of the system, or which supplier.
  3. List who decides: the rules, thresholds and settings that only a named person may change.
  4. For each line, write how it is enforced. Be candid where the only answer is an instruction to the model. Those lines go to the top of the backlog.

Short and absolute works better than long and hedged. Four lines that are each true in code are worth more than a page of principles that depend on the model behaving itself.

Job Scout has read hundreds of job adverts since its first run, and drafted a CV and letter for the best few each morning. The number of applications, replies or messages it has sent on my behalf is still zero, and that is the figure I check first.
